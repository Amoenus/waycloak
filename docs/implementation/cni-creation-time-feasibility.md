CI evidence: [run 30180813372](https://github.com/Amoenus/waycloak/actions/runs/30180813372)

## Decision

Proceed with the chained-CNI, node-owned Core architecture in ADR 0034. The
creation-time boundary is feasible on the tested Linux/containerd rows without
a sidecar or a fallback data plane.

This is a matrix-limited feasibility decision, not a stable release claim.
Every additional Kubernetes, runtime, primary-CNI, architecture and kernel row
must pass the same proof before it is supported. A cluster that prevents CNI
chaining or privileged node enforcement is unsupported; it never receives a
sidecar or ordinary-egress fallback.

The local protocol and fixture agent in this slice are feasibility surfaces.
Issue #125 must freeze their security and authentication contract before the
production node agent is implemented. No replacement CRD is generated by this
work.

## Acceptance evidence

- Exact identity: CNI arguments must contain Pod namespace, name, UID, sandbox
  ID, interface and netns. The local agent reads the exact Pod and rejects a UID
  mismatch. Durable state also records the netns device/inode identity so a
  reused path is never cleaned as the original attachment.
- Bounded wait: enrollment resolution is limited to five seconds and binding
  wait to 30 seconds by configuration validation. The proof uses a five-second
  binding wait and keeps deny state throughout retries.
- Deny before allocation: every fixture binding request attempts direct probes
  from the exact Pod netns. Independent host capture counters remain unchanged,
  proving deny is installed before the first binding request.
- Additional PR hardening makes enrollment sticky once deny state exists for an
  exact Pod UID. Runtime `DEL`, label removal and a replacement sandbox identity
  cannot turn a later `ADD` retry into unenrolled success. The record is released
  only after the exact Pod is observed terminating, or by exact stale-state GC
  when observation is unavailable. Unit and privileged homelab tests cover the
  combined race.
- Primary-CNI-then-Waycloak failure: an ordinary Pod emits positive-control
  packets before the enrolled Pod is created. The enrolled `ADD` fails after
  primary setup because its UID-bound binding is deliberately unavailable.
- Zero direct packets: positive controls are required for TCP, UDP, DNS/UDP,
  DNS/TCP and fragmented UDP. None of the five counters advances during the
  failed enrolled `ADD`.
- No application start or privilege: kubelet reports `FailedCreatePodSandBox`;
  the application has no running or terminated state, container ID or
  `started=true`. Its spec remains one application container with no init
  container, injected security context, mount or credential.
- Partial state and rollback: failure after lockdown retains durable
  `LockedDown` state for cleanup. Failure to persist the first state record
  immediately rolls back the otherwise untracked deny. Unit tests inject both
  paths.
- Restart behavior: the fixture node agent is killed and restarted while
  binding wait is active. The Kind row then restarts containerd during the same
  `ADD`; deny remains effective and the application still never starts.
- `DEL`, `CHECK` and `GC`: `CHECK` rejects a locked-down attachment. Runtime
  `DEL` after failed `ADD` retains exact-UID enrollment for a replacement
  sandbox. Terminating-Pod `DEL` performs exact cleanup. An `ADD` interrupted by
  runtime restart may leave durable state, which `GC` removes using exact
  attachment identity; two later `DEL` calls with no netns both succeed.
- Stale namespace safety: `GC` removes a record whose netns disappeared, while
  unit tests prove that a valid attachment is retained and a reused foreign
  netns is not modified.
- Chaining: `ADD` and `CHECK` require and parse `prevResult`; successful unit
  `ADD` returns only after protected-path verification. Versions `0.3.1`,
  `0.4.0`, `1.0.0` and `1.1.0` are advertised for the operations defined by
  those specifications.
